# Вимоги до модуля Data-Migration

> Цей файл оновлюється по мірі розробки. Версія: 0.2

---

## Загальний опис

Odoo-модуль **`vd_data_migration`** — додаток для міграції даних між двома Odoo 18.0 інстансами через XML-RPC.
Модуль надає UI-візард, в якому оператор налаштовує підключення до бази-джерела, обирає модель, аналізує поля та запускає завантаження даних у поточну базу.

---

## Функціональні вимоги

### FR-01: Додаток та навігація
- Модуль є **Odoo Application** (`'application': True` у маніфесті)
- У головному меню присутній один пункт — **«Міграція»**
- При виборі пункту меню відкривається **Wizard** (транзієнтна модель)

---

### FR-02: Форма візарда — підключення до джерела

Поля верхнього блоку:

| Поле | Тип | Обов'язкове | Опис |
|---|---|---|---|
| `source_url` | Char | Так | URL бази-джерела (наприклад `https://odoo-source.example.com`) |
| `source_db` | Char | Так | Назва БД на джерелі |
| `source_login` | Char | Так | Логін користувача на джерелі |
| `source_password` | Char | Так | Пароль (відображати як `password`-поле) |

---

### FR-03: Форма візарда — вибір моделі

| Поле | Тип | Обов'язкове | Опис |
|---|---|---|---|
| `target_model_id` | Many2one → `ir.model` | Так | Модель у **поточній** базі, в яку завантажуються дані |
| `record_count_source` | Integer | Ні (read-only) | Кількість записів у базі-джерелі (заповнюється після Аналізу) |
| `record_count_target` | Integer | Ні (read-only) | Кількість записів у поточній базі |

---

### FR-04: Таблиця полів (Field Mapping)

- Під полем вибору моделі розташована **табличне поле** (`One2many`) — список полів моделі
- Кожен рядок таблиці містить:

| Колонка | Тип | Опис |
|---|---|---|
| `field_name` | Char (read-only) | Технічна назва поля |
| `field_label` | Char (read-only) | Мітка поля (`string`) |
| `field_type` | Char (read-only) | Тип поля (`char`, `integer`, `many2one`, ...) |
| `source_exists` | Boolean (read-only) | Чи існує поле у базі-джерелі |
| `include` | Boolean | Чи включати поле у міграцію (за замовчуванням `True`) |
| `comodel` | Char (read-only) | Для Many2one — назва пов'язаної моделі |

---

### FR-05: Кнопка «Аналізувати»

При натисканні виконати:
1. Підключитись до бази-джерела через XML-RPC та автентифікуватись
2. Перевірити, що обрана модель (`target_model_id.model`) **існує у джерелі** — якщо ні, показати повідомлення про помилку
3. Отримати список полів моделі у джерелі через `fields_get()`
4. Зіставити з полями у поточній базі: заповнити колонку `source_exists`
5. Заповнити `record_count_source` — кількість записів у джерелі (`search_count`)
6. Заповнити `record_count_target` — кількість записів у поточній базі
7. Заповнити таблицю полів (очистити стару, побудувати нову)

---

### FR-06: Кнопка «Завантажити»

При натисканні:
1. Перевірити, що Аналіз виконано (таблиця полів не порожня)
2. Отримати записи з джерела через `search_read` батчами по **100 записів**
3. Для кожного батчу обробити записи:
   - **Прості поля** (`char`, `text`, `integer`, `float`, `boolean`, `date`, `datetime`, `selection`) — копіювати значення напряму
   - **Many2one поля** — логіка підстановки (див. FR-08)
   - Поля з `include=False` — пропускати
4. Записати у поточну базу через `create` або `write` (перевірка дублів — за наявності `name` або `external_id`)
5. Відображати **прогрес-бар** із поточним станом: `X / N записів завантажено`
6. Після завершення — показати підсумок: створено / оновлено / помилок

---

### FR-07: Кнопка «Видалити»

При натисканні:
1. Показати **діалог підтвердження**: «Ви впевнені? Всі записи моделі `<назва>` будуть видалені з поточної бази."
2. Після підтвердження — виконати `unlink()` для всіх записів обраної моделі
3. Оновити `record_count_target` → 0
4. Показати повідомлення про успіх

---

### FR-08: Обробка Many2one полів

Алгоритм для кожного Many2one значення `(id, name)` з джерела:
1. У відповідній пов'язаній моделі (`comodel`) шукати запис за полем `name` (або `id` якщо `name` відсутній)
2. Якщо знайдено — підставити локальний `id`
3. Якщо **не знайдено** — створити новий запис, заповнивши:
   - `name` = `"<{source_id}>"`  (шаблон із source id)
   - Мінімально необхідні обов'язкові поля
4. Використовувати отриманий локальний `id` для запису

---

### FR-09: Прогрес-бар

- Відображати прогрес завантаження у реальному часі
- Якщо стандартний віджет Odoo не підтримує потрібну інтерактивність — реалізувати **кастомний JS-віджет**
- Показувати: відсоток виконання, кількість оброблених / загальна кількість, поточний статус (`Завантаження...` / `Завершено` / `Помилка`)

## Нефункціональні вимоги

| ID | Вимога |
|---|---|
| NFR-01 | Логування всіх RPC-операцій через `_logger` |
| NFR-02 | Паролі тільки в пам'яті сесії, не зберігати в БД у відкритому вигляді |
| NFR-03 | Підтримка Odoo 18.0, Python 3.10+ |
| NFR-04 | Батчинг: не більше 100 записів за один RPC-запит |
| NFR-05 | Обробка помилок з'єднання: таймаут, недоступність, невірні credentials |
| NFR-06 | Модуль не має зовнішніх залежностей, тільки stdlib + Odoo |

## Відкриті питання (для уточнення)

- **OQ-01**: Чи потрібна перевірка дублів при завантаженні? Якщо так — за яким полем (`name`, `external_id`, кастомне)?
- **OQ-02**: Що робити з `One2many` та `Many2many` полями — ігнорувати або обробляти?
- **OQ-03**: Чи зберігати налаштування підключення між сесіями (окрема модель `vd.connection`), чи лише в межах одного відкриття візарда?
- **OQ-04**: Чи потрібна можливість зупинити завантаження у процесі?
- **OQ-05**: Чи логувати результат міграції у таблицю БД (журнал), чи лише у файл?

## Поза скоупом (v1)

- Міграція `ir.attachment` (файлів та зображень)
- `One2many` / `Many2many` поля — відкладено на v2
- Синхронізація в реальному часі (webhooks)
- Scheduled job (автоматична міграція за розкладом)
- Multi-company підтримка
