# Вимоги до модуля Data-Migration

> Цей файл оновлюється по мірі розробки. Версія: 0.3

---

## Загальний опис

Odoo-модуль **`vd_data_migration`** — додаток для міграції даних між двома Odoo 18.0 інстансами через XML-RPC.
Модуль надає UI-візард, в якому оператор налаштовує підключення до бази-джерела,
обирає модель, аналізує поля та запускає завантаження даних у поточну базу.

---

## Функціональні вимоги

### FR-01: Додаток та навігація
- Модуль є **Odoo Application** (`'application': True` у маніфесті)
- У головному меню присутній один пункт — **«Міграція»**
- При виборі пункту меню відкривається **Wizard** (транзієнтна модель `TransientModel`)

---

### FR-02: Форма візарда — підключення до джерела
Налаштування **зберігається тільки в пам’яті візарда** (не зберігається між сесіями і не пересипається у БД).

| Поле | Тип | Обов’язкове | Опис |
|---|---|---|---|
| `source_url` | Char | Так | URL бази-джерела (наприклад `https://odoo-source.example.com`) |
| `source_db` | Char | Так | Назва БД на джерелі |
| `source_login` | Char | Так | Логін користувача на джерелі |
| `source_password` | Char | Так | Паромь (відображати як `password=True`) |

---

### FR-03: Форма візарда — вибір моделі

| Поле | Тип | Обов’язкове | Опис |
|---|---|---|---|
| `target_model_id` | Many2one → `ir.model` | Так | Модель у **поточній** базі |
| `record_count_source` | Integer | Ні (read-only) | Кількість записів у джерелі (після Аналізу) |
| `record_count_target` | Integer | Ні (read-only) | Кількість записів у поточній базі |

---

### FR-04: Таблиця полів (Field Mapping)

- Під полем вибору моделі розташована **таблиця полів** (`One2many`) — видима всі типи полів, включаючи Many2one, One2many, Many2many
- Кожен рядок таблиці містить:

| Колонка | Тип | Опис |
|---|---|---|
| `field_name` | Char (read-only) | Технічна назва поля |
| `field_label` | Char (read-only) | Мітка поля (`string`) |
| `field_type` | Char (read-only) | Тип поля (`char`, `many2one`, `one2many`, ...) |
| `source_exists` | Boolean (read-only) | Чи існує поле у базі-джерелі |
| `include` | Boolean | Чи включати поле у міграцію (`True` за замовчуванням; для `one2many` встановити `False`) |
| `comodel` | Char (read-only) | Для Many2one/Many2many/One2many — назва пов’язаної моделі |

---

### FR-05: Кнопка «Аналізувати»

При натисканні виконати:
1. Підключитись до бази-джерела через XML-RPC та автентифікуватись
2. Перевірити, що обрана модель **існує у джерелі** — якщо ні, показати повідомлення про помилку
3. Отримати список полів моделі у джерелі через `fields_get()`
4. Зіставити з полями у поточній базі: заповнити колонку `source_exists`
5. Заповнити `record_count_source` через `search_count`
6. Заповнити `record_count_target`
7. Очистити таблицю і побудувати яї знову

---

### FR-06: Кнопка «Завантажити»

При натисканні:
1. Перевірити, що Аналіз виконано
2. Отримати записи з джерела через `search_read` батчами по **100 записів**
3. Для кожного запису з джерела:
   - **Шукати у поточній базі запис з таким самим `id`** (обробка `external_id` або `xmlid`)
   - Якщо знайдено — **перезаписати** через `write()`
   - Якщо не знайдено — **створити** через `create()`
4. Обробка полів залежно від типу:
   - **Прості** (`char`, `text`, `integer`, `float`, `boolean`, `date`, `datetime`, `selection`) — копіювати напряму
   - **`many2one`** — логіка підстановки (FR-08)
   - **`many2many`** — логіка підстановки (FR-09)
   - **`one2many`** — в v1 пропускати (встановлюється `include=False` автоматично)
   - Поля з `include=False` — пропускати
5. Відображати **прогрес-бар** із поточним станом
6. Підтримувати можливість **зупинити** (FR-10)
7. Після завершення — показати підсумок: створено / оновлено / помилок

---

### FR-07: Кнопка «Видалити»

При натисканні:
1. Показати **діалог підтвердження**: «Ви впевнені? Всі записи моделі `<назва>` будуть видалені з поточної бази.»
2. Після підтвердження — виконати `unlink()` для всіх записів обраної моделі
3. Оновити `record_count_target` → 0
4. Показати повідомлення про успіх

---

### FR-08: Обробка `many2one` полів

Значення Many2one з джерела приходить як `(source_id, name)`.

Алгоритм:
1. У відповідній пов’язаній моделі (`comodel`) шукати запис за `id` (search by `id` = `source_id`)
2. Якщо знайдено — підставити локальний `id`
3. Якщо **не знайдено** — створити новий запис:
   - `name` = `"<{source_id}>"` (шаблон)
   - Мінімально необхідні обов’язкові поля
4. Використовувати отриманий локальний `id`

---

### FR-09: Обробка `many2many` полів

Значення Many2many з джерела приходить як список `[id1, id2, ...]`.

Алгоритм:
1. Для кожного `source_id` зі списку — застосовувати алгоритм FR-08
2. Зібрати локальні `id` для всіх елементів
3. Записати як `[(6, 0, [local_id1, local_id2, ...])]`

---

### FR-10: Зупинка завантаження

- Під час завантаження доступна кнопка **«Зупинити»**
- Після натискання встановити внутрішній флаг `_stop_requested = True`
- Після обробки поточного батчу перевіряти флаг: якщо `True` — зупинити обробку
- Показати повідомлення: «Завантаження зупинено користувачем. Оброблено X / N записів.»
- Можливо використання кастомного JS-віджета (однаковно з прогрес-баром)

---

### FR-11: Прогрес-бар і кастомний віджет

- Відображати прогрес завантаження у реальному часі
- Якщо стандартний Odoo-віджет не підтримує потрібну інтерактивність — реалізувати **кастомний JS-віджет** (`ProgressBarWidget`)
- Віджет показує:
  - Візуальна полоска (`0%` → `100%`)
  - Лічильник: `X / N записів`
  - Статус: `Завантаження...` / `Завершено` / `Зупинено` / `Помилка`
  - Кнопка **«Зупинити»** (FR-10)

## Нефункціональні вимоги

| ID | Вимога |
|---|---|
| NFR-01 | Логування всіх RPC-операцій через `_logger` |
| NFR-02 | Налаштування зберігається лише в пам’яті візарда, не пересипається в БД |
| NFR-03 | Підтримка Odoo 18.0, Python 3.10+ |
| NFR-04 | Батчинг: не більше 100 записів за один RPC-запит |
| NFR-05 | Обробка помилок: таймаут, недоступність сервера, невірні credentials |
| NFR-06 | Модуль без зовнішніх залежностей, тільки stdlib + Odoo |
| NFR-07 | Логування результату міграції лише у файл/консоль (Odoo `_logger`), не в БД |

## Поза скоупом (v1)

- Міграція `ir.attachment` (файлів та зображень)
- `one2many` поля — відображаються в таблиці, але `include=False` за замовчуванням
- Синхронізація в реальному часі (webhooks)
- Scheduled job (автоматична міграція за розкладом)
- Multi-company підтримка
- Збереження налаштувань підключення між сесіями (окрема модель)
- Журнал міграцій у таблицю БД
